# Kea DHCP 管理

管理现有 Kea DHCPv4 Control Agent，使用服务端固定配置的两台 API 地址和专用 Basic Auth 账号。浏览器不会收到 API 密码，也不能指定任意管理接口或执行任意 Kea 命令。

## 功能

- 合并两台的 IPv4 租约副本，显示 MAC、主机名、到期时间和 A/PTR 更新标记。
- 子网新增/编辑/删除：地址池、网关、DNS 服务器、域名、搜索域、默认租期。
- 基于 MAC 的保留地址新增/编辑/删除，也可以从现有租约填入保留地址表单；支持逐设备网关、DNS、域名、搜索域、NTP 和 MTU。
- 保留地址的高级设置包括网络启动服务器/名称/文件、客户端分类、备注与标准/自定义/厂商 DHCP 选项，支持 CSV 或十六进制值及发送策略。
- 释放服务端租约、请求 Kea 重发 DDNS。
- HA 节点角色、状态、伙伴通信、版本和子网配置一致性。

新建子网不会自动配置路由器、VLAN 或 DHCP relay。删除子网要求没有有效租约和保留地址。编辑现有子网不允许修改前缀，也不允许把仍有效的普通租约排除到地址池之外。

### 保留地址选项

网络设置留空时不写入主机覆盖项，继续使用所属网络的设置；填入值时只覆盖此设备，清空并保存可恢复继承。表格显示网关和 DNS 的已配置结果及继承标记，固定各列比例；手机使用卡片展示。继承显示合并了全局、显式分配的分类、共享网络、子网及匹配的地址池。依赖客户端报文动态匹配的分类在请求时由服务端决定，页面不能据此预测所有客户端的最终应答。

普通编辑保留未涉及的字段和选项元数据。附加选项与网关/DNS 等常用字段分开管理，禁止重复、冲突或通过附加选项覆盖同一常用设置。自定义和厂商选项需要已有相应定义，最终配置由两台节点原生校验。备注只修改 `user-context.comment`，保留其他业务元数据。设置在客户端后续获取/续租时生效，不会强制断开或刷新客户端。

域名和搜索域是下发给客户端的 DHCP 选项，既有 DDNS 区域、TSIG、DHCID 及更新策略继续保留。网络启动固定字段与选项 66/67 分开配置，避免将不同客户端读取的协议字段混为一项。主机保留地址没有独立的 `valid-lifetime` 字段；租期仍由所属网络或分类策略控制。相关行为见 [Kea 3.0 主机保留地址文档](https://kea.readthedocs.io/en/kea-3.0.0/arm/dhcp4-srv.html#including-specific-dhcpv4-options-in-reservations)。

### 保留地址与静态服务器名称

租约根据所属子网和 MAC 关联保留配置，地址尚未续租到保留 IP 时也能识别。已有保留地址显示“编辑保留”，打开原配置并保留设备选项；新建使用独立的 `reservation-create` 操作，同一子网重复 MAC 返回 409，不会覆盖原记录。不同子网可以配置同一 MAC。

DNS 维护方式可选择“静态维护”或“动态注册”。静态维护使用可写主区域（优先 `intra`）的绝对名称，例如 `server.intra.example.com.`，并在主机保留配置中添加 `SKIP_DDNS` 分类，阻止后续续租、释放等操作自动改写静态解析。两台必须预先正确加载 `libdhcp_ddns_tuning.so`，且显式配置 `"parameters": {}`；新增组件应先通过独立进程的 `kea-dhcp4 -T` 校验实际加载，不能仅依赖 API `config-test`。应用不会安装组件或扩大 TSIG 权限。

静态 A/PTR 记录在 DNS 管理流程中单独维护。选择此方式不会自动创建解析，也不会改写历史租约；切换已有设备时应备份并核对静态 A/PTR、旧动态名称及 DHCID，必要时保留旧名称直到缓存过渡完成。租约页面保留原始租约名称，并单独显示保留配置指定的静态名称；保留配置本身不能证明设备目前使用 DHCP 获取地址。域名/搜索域选项与 DNS 注册名称分别管理。

静态维护设备禁止重发 DDNS；释放租约时保留静态 DNS。动态注册设备继续沿用所属网络的动态注册区域和所有权规则。

## 双节点配置流程

先读取两台完整配置，在各自配置副本上修改指定子网，保留每台自身的 HA、DDNS、分类和其他选项。两台必须连通、处于正常 HA 状态且子网配置一致。配置版本过期返回 409。

1. 对两台执行 `config-test`；预览请求到此为止。
2. 写入审计意图；审计不可写则不发送配置变更。
3. 再次比对配置，先更新配置列表第二台（约定为备用节点），再更新第一台（主节点）。各自执行 `config-set` 和 `config-write`。
4. 失败时按反向顺序重新应用已尝试节点的原配置；即使 `config-get` 返回原 JSON，也需要恢复可能因钩子加载失败而丢失的运行状态。发现配置被其他端修改、无法确认响应或回滚失败时保留 PENDING，要求核对节点。

Kea 的 API 不提供跨节点事务或原子配置版本比较。控制台串行化自身的写操作，仍应避免同时使用其他管理端改同一配置。进程意外终止或部分节点持久化失败时，需要结合审计前后内容与部署前备份手工恢复。

子网/保留地址通过完整配置中的目标子网变更实现，不依赖 Host Commands hook。Kea `subnet4-update` 不接受静态保留地址，不能直接用于保留地址管理。参考 [Kea 3.0 官方命令说明](https://kea.readthedocs.io/en/kea-3.0.0/arm/hooks.html#the-subnet4-update-command)。

## 租约和 DNS

租约分页读取，当前最多每节点 20,000 条。释放时在两台删除服务端记录，动态注册设备由第一台请求清理 DDNS，静态维护设备保留解析；这不会主动断开客户端，客户端可能仍使用原地址直到重新获取。重发 DDNS 由第一台 Kea 发起，并遵循已有 D2、TSIG 和所有权策略。租约操作失败不自动重试，结果不明保留 PENDING。

DNS 面板继续禁止人工改写 Kea 管理区域。DHCP 功能通过 Kea 命令操作租约和配置，保留既有 DNS 联动。

## 配置

在 `.env` 设置 `INFRAPILOT_DHCP_ENABLED=true`、`INFRAPILOT_KEA1_API_URL`、`INFRAPILOT_KEA1_API_USERNAME`、`INFRAPILOT_KEA1_API_PASSWORD` 和第二台相同变量。第一台应为主节点，第二台为备用节点。生产密码使用随机值，Kea API 仅向应用宿主机开放。配置文件和环境文件应受操作系统权限保护，不提交 Git。
